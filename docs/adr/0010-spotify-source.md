# ADR 0010. Spotify как второй источник автозаполнения

Статус: принято · 2026-09-26 · дополняет ADR 0004, ADR 0006

## Контекст

iTunes (ADR 0004) не всегда покрывает то, что есть в привычной библиотеке пользователя. Обсуждали
Яндекс.Музыку и Spotify. У Яндекс.Музыки нет официального публичного API — только реверс-инженерный,
без CORS для чужого браузерного кода и без явной поддержки, поэтому под архитектуру «всё в браузере,
без сервера» не подходит. У Spotify — официальный Web API; CORS для `api.spotify.com` и
`accounts.spotify.com/api/token` подтверждён напрямую из браузера перед началом работы (реальные
статусы 401/400 вместо блокировки).

## Решение

1. **Вход — Authorization Code + PKCE**, без client secret вообще (secret пришлось бы либо держать в
   клиентском коде публично, либо заводить свой сервер). Владелец создаёт приложение на
   developer.spotify.com/dashboard, получает только Client ID, вводит его в Настройки → Источники →
   «Войти через Spotify» (`src/components/SpotifySettings.tsx`). В Redirect URIs кабинета Spotify нужно
   добавить оба адреса — дев-сервер и адрес сайта — по отдельности, редирект возвращается на тот же
   адрес, с которого ушли.
2. **PKCE-механика** — `src/services/spotifyAuth.ts`: `code_verifier`/`state` в `sessionStorage` на
   время редиректа, `code_challenge` через `crypto.subtle.digest('SHA-256', …)`. Spotify возвращает
   `?code=…` обычной query-строкой (не хэшем) — не пересекается с hash-роутером; обрабатывается один
   раз при старте (`handleAuthCallback`, вызов из `init()` в `store/app.ts`, до остальной загрузки).
3. **Токены** — `access_token` (1 ч) и `refresh_token` (бессрочный, тоже обменивается без secret) в
   meta `LocalSource`, как токен GitHub: только на устройстве владельца. `getValidToken` тихо
   обновляет токен за минуту до истечения.
4. **Обложка Spotify не загружается.** У `i.scdn.co`/`spotifycdn.com` нет CORS для `fetch()` —
   проверено на реальном URL (через открытый `open.spotify.com/oembed`, без токена): браузер не даёт
   прочитать байты, только показать `<img>`. Через canvas сжать нельзя, а `LocalSource`/публикация на
   GitHub (ADR 0007) работают с байтами, не со ссылками. Раз частичный успех лучше отказа (ADR 0006,
   п.3) — `src/services/spotify.ts` не пытается: редактор открывается без обложки, владелец добавляет
   свою или переключается на iTunes для этого альбома.
5. **iTunes остаётся первым источником**, Spotify — переключатель рядом с формой поиска
   (`src/screens/AddSearch.tsx`), выбор запоминается в `localStorage`. Не заменяет iTunes: у каждого
   свои пробелы в каталоге.
6. **Формат данных** — `spotifyId?: string` в `Release`, рядом с `itunesId`. Чисто добавочное поле,
   `FORMAT_VERSION` не трогаем (в отличие от переименования `mbid → itunesId` в ADR 0004, здесь ничего
   не убираем и не переименовываем).
7. **Тип релиза** Spotify не различает EP отдельно от сингла в ответе API — `album_type` только
   `album`/`single`/`compilation`. Оставляем на правку владельцу в редакторе, как и не самые точные
   случаи с iTunes.

## Известное ограничение (2026-09-26)

Web API отвечает 403 на `/v1/search` и подобные запросы, если у аккаунта, на котором создано
приложение в кабинете Spotify (не у аккаунта, который логинится через PKCE — это может быть один и
тот же человек, но проверяет Spotify именно владельца приложения), нет активной подписки Premium:

> Active premium subscription required for the owner of the app. When the subscription status
> changes, it can take a few hours before requests are allowed again.

Это ограничение самого Spotify, появившееся уже после того, как ADR был принят — не баг в коде.
Текст ошибки виден пользователю как есть (`src/services/spotify.ts`, `errorDetail`). Проверено на
реальном приложении без Premium — 403 воспроизводится стабильно. Код рабочий и не требует
изменений: заработает сам, как только на аккаунте владельца приложения появится Premium (по словам
Spotify — с задержкой в несколько часов после смены статуса подписки).
